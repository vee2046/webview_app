关键状态

states 每个状态都给出「用户下一步能做什么」，而不是只报错

离线进入

无网络时点击已缓存的工具 → 直接加载本地副本，顶部显示「离线模式」标记。

✅ 行为：能用的照常能用，只是提示当前无网

远端加载失败

目标 URL 打不开（改版/下线/404）且本地无副本。

✅ 行为：给出「重试 / 用浏览器打开 / 反馈该工具」三个出口，而不是白屏

配置拉取失败

远程 config 超时或格式非法。

✅ 行为：静默沿用内置快照 + 上次可用配置，首页照常渲染

工具被下线

远端 config 里该工具 enabled:false。

✅ 行为：首页隐藏，但「最近使用」仍保留入口并标注「已下线」

新工具热更

远端 config 增加了工具，App 冷启动后出现。

✅ 行为：卡片带「NEW」角标，7 天后自动消失

存储空间不足

WebView localStorage / IndexedDB 写满。

✅ 行为：引导导出备份后清理某工具数据，不动其他工具

冷启动时序

launch sequence
1
读内置快照

毫秒级出首页，不等网络。首屏永远有内容（沿用 kmlab_site 的双轨策略）。

2
渲染首屏

卡片、筛选、最近使用全部用快照渲染，用户可立即点击。

3
后台拉远端配置

8 秒超时；成功后校验 → 原子替换 → 差异高亮（新增卡片闪一下）。失败则完全静默。

4
按需预取离线包

Wi-Fi 下静默预缓存常用工具；蜂窝网络下先问一次。

5
注入 Bridge

页面加载完成后注入 window.KM，并回传标题、favicon、状态。

技术选型对比

stack options
方案配置渲染WebView 控制力跨平台体积结论
Android 原生
Kotlin + Compose		 配置 → Compose 状态，中等成本 最强（WebViewAssetLoader、缓存、拦截全可控） 仅 Android 最小 若只做 Android，这是最优解；你已有 autopass 的 Compose 栈
Flutter
Dart + webview_flutter		 配置 → Widget 树，成本低 中（需 PlatformView 桥接做拦截） Android + iOS 中 跨平台首选；你已有 brainfit 的 Flutter 工程与设计系统
Capacitor
Web 技术栈		 最自然（JSON 直接喂 Vue/React） 弱（靠官方 WebView 插件 + JS 桥） 全平台 中 配置渲染最省事；但 WebView 定制（缓存/拦截）能力有限

💡 推荐：Flutter。理由 —— ① 跨平台一次开发；② 配置 → Widget 的映射成本最低； ③ 你已有的 Flutter 设计系统（brainfit）可直接复用；④ 后续若要上架应用商店，Flutter 出包链路成熟。

配置校验与降级

validation

✅ 接受的规则

  • 缺字段 → 用默认值补齐（subtitle 空、color 走默认墨线色）
  • 未知字段 → 忽略并记录日志，不报错
  • 工具 id 重复 → 后者覆盖前者并告警
  • 非法 URL → 该卡片降级为「不可用」灰态，其余工具照常
  • 图标名不存在 → 回退到默认盒子图标

⚠️ 拒绝的规则

  • schemaVersion 更高（App 太旧）→ 拒绝整份远端配置，沿用内置快照
  • JSON 解析失败 → 沿用上次可用配置
  • 签名不匹配（开启校验时）→ 拒绝，记安全日志
  • tools 为空数组 → 视为非法（防止误清空首页）
  • 单个工具字段类型错 → 只丢这个工具，不影响整份配置

设计决策

decisions & risks 每一条都标了「为什么」和「代价」

🟢 D17 · 工具顶栏常驻，不自动隐藏

auto 档不再自动收起顶栏 —— 一旦显示就一直。要沉浸请明说，用 immersive 档（真全屏 + 顶部热区唤出）。

  • 为什么：很多工具（药品 / 宝盒 / 任务清单）内容不满一屏，顶栏凭空消失会让人以为页面坏了、App 卡了。
  • 代价：「省 44px」的收益远小于「用户以为出问题了」的代价。
  • 连带清理：autoHideDelayMs / isAutoChrome / scrollScript / onScrollDirection 全部删除（不留死代码）。

🟢 D18 · 点工具卡片不做特例：一律进配置的 url

删掉 open.mode 字段与 external / browser 两种打开方式。所有工具 —— 包括「井条条」这种本身是外部项目的 —— 点卡片都在 App 内的 WebView 里打开配置里的 url。

  • 为什么：同一个列表里「有的进 App、有的跳出去」= 行为不一致，用户每次都要重新判断；外部跳转还多一个中间弹窗。
  • 想跳出去？：⋯ 菜单里一直有「在浏览器中打开」。
  • 代价：外部页面在 App 内打开没有原生 App 体验（登录态 / 推送）—— 可接受，这些页面本来是「看一眼」。

🟡 D16 · 顶栏右侧只留一个图标：网格 ⇄ 列表

「最近」页和「小工具」页的顶栏右侧各只保留一个按钮 —— 切换这两页数据的显示格式（卡片 / 列表）。两页共用同一个开关。

  • 去掉齿轮：底部导航本来就有「我的」，顶栏再放一个跳页按钮 = 重复入口；而且一堆图标里混着「跳页」和「刷新」两种语义，用户点之前得先猜 —— 这就是「功能混乱」的来源。
  • 「刷新远端配置」下沉到「我的」页（那里本来就有刷新按钮）。配置启动时本来就静默刷新，手动刷新是低频动作。
  • 两页共用一个开关（ViewPrefs）—— 同一份数据、同一套排版偏好，不给用户「两处设置」的机会。
  • 层级：配置 app.home.layout 是默认值；用户手动切过一次后以用户为准并持久化到本机（配置再变也不覆盖）。
  • 表现：小工具页 = 2 列卡片 ⇄ 每行一个；最近页 = 时间线 2 列卡片 ⇄ 时间线紧凑行（续接卡和常用两种排版都一样）。

🟡 D15 · 当前只做 Android，iOS / macOS 暂缓

暂不开通 Apple 开发者账号（$99/年），迭代范围收窄到 Android；iOS / macOS 的代码与工程保留（已跑通、已出包），但不签名分发、不上架、不投入。

  • 账号是同一个卡点：TestFlight 要付费账号；iOS 离线要的 app-bound 域名验证（Associated Domains + 站点 AASA + 真机签名）同样要付费账号。
  • Android 侧该有的能力全都有了：Service Worker 离线（实测断网秒开）、原生 Toast、下载拦截、外链交接、分享面板、灰度、签名校验、配置 diff。
  • 沉没成本几乎为零：Dart 层三端共用，账号将来齐了，iOS/macOS 的代码仍在、坑也已记录（DESIGN §5.9 / BUG #27），随时捡起来。
  • 代价明说：没有 App Store / TestFlight 分发渠道，Android 侧靠 release APK 侧载；macOS 桌面版一并搁置。

🟢 D14 · 名称 / 图标 / 分类 复用 kmlab_site

App 不是「另一个品牌」，而是 kmlab_site 的移动端形态。所有可复用的东西都从 kmlab_site 直接搬，不另起一套。

  • 名称：kmlab（site.name）+ handmade workspace（header.brandSub）；底部导航第二项叫「小工具」（projects.navLabel）。
  • App 正式名：kmlab Toolbox（纯英文）。站点的 <title> 是「kmlab · 工具」——中英混排，桌面图标标签用着别扭，所以 App 侧刻意改成纯英文；app.brandSource 里留了 pageTitle 记录站点原值。
  • 图标：App 图标 = kmlab_site/public/favicon.svg；工具图标 = DoodleIcon.vue 的 9 个 doodle，路径逐字照搬。
  • 分类：life 生活习惯 / productivity 效率清单 / knowledge 知识索引 / misc 其他，id、label、颜色全部沿用，关键词匹配规则也一致。
  • 工具名：直接取 html_files.json 的 title，改版只需改一处。
  • 配置里留了溯源：app.brandSource 逐项写明来自 kmlab_site 的哪个文件，将来同步不会断线。

🔴 最大坑：换 origin = 丢数据

所有工具当前用 localStorage（key 如 baobox.v1、medicine_tracker_v1）， 数据存在 https://kmlab.tech 这个 origin 下。

  • 如果 App 改为加载内置离线副本（appassets.androidplatform.net 或 file://）， 就是另一个 origin → 另一个存储空间 → 用户在网页版攒的数据全部不可见。
  • 决策：默认走远端 origin，与网页版共享数据；离线能力用「缓存副本 + 显式导入导出」补齐， 而不是在存储层面偷换 origin。
  • 代价：首次打开任一工具需要一次网络。

🟢 为什么「同源共享」反而是优点

  • 用户只在网页版用过的数据，App 里直接可见，零迁移成本。
  • 工具的 localStorage key 本就不冲突（baobox.v1 / medicine_tracker_v1 / water 系列）， 共存没有风险。
  • 用户偏好（字体大小、主题）也能跨工具共享 —— 前提是各 H5 用同一 key 约定， 这需要给 h5_tools 补一份存储 key 规范。

🟡 配置双轨 = 和 kmlab_site 同构

kmlab_site 已经是「构建期内置快照 + 运行时同源静默刷新 + 失败降级」。 App 直接复用同一套心智：首屏永远有内容，配置永远能热更。

  • 好处：断网、配置被删、服务器挂了，App 都照常能用。
  • 代价：多一份 last-good 持久化逻辑（很小）。
  • 实测补充：静态托管的 SPA 对不存在的路径返回 200 + index.html， 所以远端响应要做内容嗅探（首字符必须是 {）而不是只看状态码。
  • 新鲜度保护：配置带 generatedAt 时间戳，远端比 App 内置的旧 （或缺这个字段）一律拒绝并沿用本地 —— 防止站上构建产物没更新，把 App 刚修好的功能打回去。
  • 「配置即契约」守卫：实跑审计揪出 8 个假开关 （javascriptEnabled / cacheMode 等 —— 平台压根没有对应 API）。 已从配置与模型里删干净，并加了一条单元测试：配置里再出现没人读的字段，测试直接红。 假开关比没有开关更糟 —— 运营会以为改它有用。

🟣 Bridge 该做到什么程度

原则：增强而非依赖。每个 H5 在没有 App 的浏览器里必须原样可用。

  • 必须：KM.openTool / KM.setTitle / KM.toast / KM.share / KM.exportData
  • 可选：KM.vibrate / KM.theme / KM.track
  • 禁止：让 H5 依赖 Bridge 才能跑；Bridge 挂了 H5 必须还能用
  • Bridge 注入时机：document start 注入壳、DOMContentLoaded 后通知 H5 就绪

🔵 App 与 H5 的职责边界

App 负责外壳导航、配置渲染、WebView 生命周期、下载/外链/权限拦截、离线包、数据备份、主题
H5 负责业务逻辑、业务 UI、数据读写（localStorage/IndexedDB）、业务级导出
共享契约storage key 命名规范 + Bridge API + 配置字段语义

🟡 D7 · 首屏为什么是「最近」

  • 使用动机：打开 App 的动作 = 「我要接着干活」，不是「我要逛工具」。首屏给目录 = 每次都多一次点击。
  • 但：首屏 = 最近 意味着「最近」必须升级成一级页面，不能只是首页里的一小块列表。
  • 因此它需要三块内容：「继续」卡（上次干到哪）、常用（手动置顶）、时间线（今天/昨天/更早）。
  • 风险：首次安装空白 → 空状态直接给推荐工具 + 去工具箱的出口。
  • 代价：首页默认落点从「工具」变成「最近」，喜欢逛目录的用户要多点一次。

🟡 D8 · 全屏的四档 chrome

目标：header 与 footer 都不显示，把竖向空间 100% 让给 H5。但不能「真的什么都没有」—— 否则用户在 iOS 上（没有硬件返回键）会困死在里面。

  • minimal（默认）：顶部 36px 极简栏 = ← + ⋯，无底部条。低频操作全收进 ⋯ 菜单。
  • auto：滚动时整条栏淡出，停止 1.5s 淡回；上滑临时唤出。适合长文型工具。
  • immersive：真全屏，无 header 无 footer，可选连系统状态栏一起藏。
  • full：完整顶栏 + 完整底条，仅在需要展示 URL / 显式分享时用。

逃生通道（三条，缺一不可）：① 顶部热区下滑（iOS 必需） ② 硬件返回键（Android）③ 双指下滑（系统级）。

实跑补充：Android 上 WebView 是 PlatformView，在原生视图层级里会盖住 Flutter 的手势层 → 顶部热区手势必须由页面 JS 监听后回传（KM.edgeSwipe），不能只靠 Flutter 的 GestureDetector；唤出工具栏后 Flutter 覆盖层上的按钮仍可点。

代价：chrome 隐藏后加载进度条也看不见 → immersive 下用骨架屏/首屏闪屏代替；失败兜底页在任何档位都必须保留。

🟢 D10 · 返回键默认不接管页面内路由（可按工具开启）

默认 routeBackEnabled:false —— 返回键一律回最近页，不调 goBack()。 需要时可按工具逐个打开这个开关。

  • 实测结论：喝水/打卡/药品/月光/任务/AGI 之路 —— 源码 0 处 pushState、0 处 hash 路由，确实是单页。
  • App 一旦接管 goBack()，就会和 H5 自己的路由形成两套历史栈，行为不可预测。
  • 「退出工具」比「退一步」更符合直觉 —— 工具在 App 里是独立页面，不是网站。
  • 开关：open.routeBackEnabled（布尔，默认 false）+ open.backFallback（home 回首页 / exit 退出 App）。全局默认在 webview.routeBackEnabledDefault。
  • 脑力慢养也不开 —— 它虽是 hash 路由 SPA（#/game/A~E、#/records…），但页内本就有「回到首页」按钮，不需要 App 帮它退；保持 8 个工具行为一致比给一个特例更值。
  • 代价：任何多路由的 H5 都无法用系统返回键回退 —— 但这正是「默认关闭」想控制的复杂度；真需要时配置里开一个字段即可。

🟡 D11 · 顶栏只留一个 ⋯

12 个低频动作全收进分组 Action Sheet：页面 / 显示 / 数据 / 关于。

  • open.overflowItems 既是白名单也是顺序，逐工具裁剪（井条条只留 4 项）。
  • clearData 必须二次确认，并写明「只清这个工具，不影响其它工具」+ 提示先备份。
  • exportData 导出该工具自己的存储（见 D12）；App 级「导出全部数据」在「我的」页，两者不重复。
  • fullscreen 只改当前会话，不写回配置，下次进入仍按 open.chrome。
  • immersive 档位下没有 ⋯ 按钮（完全无 chrome），要靠顶部热区唤出工具栏才够得着。

🟢 D12 · 导出 = .json 文件 + 系统分享面板

选「导出这个工具的数据」→ 生成 .json → 交给系统分享面板（Android ACTION_SEND / iOS UIActivityViewController）。

  • 为什么是文件不是剪贴板：剪贴板只适合小段文本；工具数据动辄几十 KB，塞剪贴板既不稳又不安全（剪贴板会被别的 App 读）。
  • 一条路走通：发微信 / 飞书 / 邮件、存「文件」再上传网盘、AirDrop 到电脑 —— 都是系统分享面板的原生能力，不用自己造。
  • 换机闭环：导出 → 传到新机 → 「导入数据」选回这个文件 → 覆盖恢复。
  • 文件名可配：webview.dataTransfer.exportFileName = "km-{toolId}-backup-{yyyyMMdd}.json"，带上工具名和时间，落到「文件」里一眼认得出。
  • 剪贴板只作兜底（clipboardFallback:true）：分享面板被禁或用户想快速粘贴时用，容量小则提示改用文件。
  • 导入侧：importEnabled / importMaxSizeMb（默认 10MB）/ importConflictPolicy:"confirm"（同名 key 问用户覆盖还是合并），不静默覆盖。
  • 「清除数据」放在 ⋯ 里，已定：二次确认 + 明确写「只清这个工具，不影响其它工具」+ 引导先导出。

🟢 D13 · 「清除数据」放在 ⋯ 菜单里

保留在 ⋯ 的「数据」组，但用最高规格的防护。

  • 二次确认弹窗写明「只清除 {工具名} 的数据，不影响其它工具」
  • 弹窗里给「先导出备份」按钮 —— 把危险操作和救援操作放在一起
  • 危险色（红）+ 独立的「取消」按钮，避免误触
  • 与 D12 配套：清之前先导一份，是唯一可靠的回退路径

R4h5_tools 的 list/ 与 mindx/ 是上游构建产物，不能直接改中不编辑产物；离线包与 SW 由 h5_tools 仓库旁挂额外文件（sw.js）实现，不侵入上游代码
R5续接卡摘要依赖各 H5 的 localStorage 结构，尚未统一✅ 已解决key 清单已实测交付（docs/STORAGE_KEYS.md），6 种摘要算法；无法解析时自动降级为「还没开始」
R6远端配置被篡改低可选 HMAC 签名校验（remote.requireSignature），默认开
R7App 图标需各平台多尺寸位图✅ 已消除scripts/generate-icons.sh 用 ImageMagick 从 SVG 自动生成（Android 传统/自适应/单色 + iOS 全尺寸，iOS 端严格按 Contents.json 的文件名）
R88 个工具的 localStorage 结构各不相同，导出 JSON 难统一低统一包一层 {toolId, version, exportedAt, storage:{}, idb:{}}；导入按 toolId 分发，各工具自己解析
R9html_files.json 与 app.config.json 两份清单可能不同步低app.config.json 是 App 的唯一真相源；站内清单只作参考，运营只改 app.json
R10远端配置发布滞后，会把 App 打回旧行为中配置带 generatedAt 时间戳；远端比本地旧（或缺这个字段）一律拒绝并沿用本地
R11WebView 是 PlatformView，Flutter 盖在上面的手势层收不到落在 WebView 区域的触摸中需要页面内手势时由页面 JS 监听后回传，不靠 Flutter 的 GestureDetector；Flutter 覆盖层上的按钮仍可点
R12iOS 上没有离线能力 —— iOS 的 WKWebView 只在「已验证的 app-bound domain」里才暴露 navigator.serviceWorker（macOS 实测可用，只有 iOS 不行）低 · 已搁置如实显示「此平台不支持（需域名验证）」而不是假装能离线；千万别加 WKAppBoundDomains —— 声明它会让所有 WKWebView 进入严格模式、整个 JS Bridge 全废；拿到 Apple 账号后按 DESIGN.md §5.9 的四步开。当前只做 Android（见 D15），此项已搁置
R13Android 没有正式分发渠道 —— 没有 Google Play 开发者账号，release APK 只能靠侧载；且 release 目前仍用 debug key 签名中侧载够用（./scripts/build-android.sh --install 一条命令出包并装机，覆盖安装保留数据）；要上 Play 需自建 keystore（key.properties 放本地、不入库）
